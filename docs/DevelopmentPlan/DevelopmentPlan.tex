\section{Workflow Plan}

The team will use GitHub for version control, issue tracking, project planning,
and code review. The \texttt{main} branch will contain stable,
production-ready code, while new features and fixes will be developed on
separate branches. Each branch will address a specific GitHub Issue
and will be merged into \texttt{main} through a pull request (PR). The PR will
describe the changes, identify the linked issue, and summarize the testing that
was performed. Before the PR is merged, at least one team member other than the
author must review and approve it.

\noindent \textbf{GitHub Issues} will be used to track features, bugs, questions, and technical tasks. Issue templates will be created for common tasks such as feature requests and bug reports. Issues will be assigned to team members and linked to relevant milestones.
\\\\
\noindent \textbf{GitHub Labels} such as \texttt{feature}, \texttt{bug}, \texttt{documentation}, \texttt{frontend}, \texttt{backend}, and \texttt{AI/ML} will be used to categorize and organize issues. Priority labels such as \texttt{high}, \texttt{medium}, and \texttt{low} will be used to indicate the urgency of each issue.
\\\\
\noindent\textbf{GitHub Projects} will be used as a project board to track issues through \texttt{Backlog}, \texttt{Ready}, \texttt{In Progress}, \texttt{In Review}, and \texttt{Done} statuses. The board will be reviewed during team meetings to identify blocked or overdue work, manage dependencies, and adjust priorities.
\\\\
\noindent\textbf{Milestones} will be used to group issues according to major project phases 
and deliverables, allowing the team to track progress and identify outstanding work. 
For example, for this project milestones will likely include \texttt{MVP}, 
covering course-outline data extraction and policy checking, and \texttt{Final Release}, covering assessment conflict identification, scheduling suggestions, database exports, testing, and documentation.
\\\\
\noindent\textbf{Continuous Integration/Deployment:} GitHub Actions will be used for CI to automatically run tests, linting, and formatting checks on pull requests. Changes merged into \texttt{main} will be deployed automatically where practical.
\\ \\
\noindent\textbf{Development Workflow:}
\texttt{Issue $\rightarrow$ Feature Branch $\rightarrow$ Implementation $\rightarrow$ Pull Request $\rightarrow$ CI Checks $\rightarrow$ Code Review $\rightarrow$ Merge $\rightarrow$ Deployment}.

\section{Proof of Concept Demonstration Plan}

% What is the main risk, or risks, for the success of your project?  What will you
% demonstrate during your proof of concept demonstration to convince yourself that
% you will be able to overcome this risk?

The main risk for this project is extracting reliable information from course
outlines. CAS course outlines do not follow one standard format. Different
instructors use different layouts and file types, and some information may be
missing or incomplete, such as ``Midterm Date: TBD''. Since most of the system
depends on this information, including the shared calendar, conflict detection,
scheduling suggestions, and compliance checking, the extracted data needs to be
accurate. If assessment dates, weights, or learning outcomes are extracted
incorrectly, the rest of the system will also produce unreliable results.

Another major risk is turning the scheduling problem into something that can
actually be solved. The team plans to use the CP-SAT solver from Google
OR-Tools. The difficult part will be converting things such as assessment dates,
student cohorts, exam periods, and policy restrictions into constraints that the
solver can work with. 

There are also a few smaller risks. LLM-generated explanations may not always be
accurate, and the model may eventually need to be hosted on CAS servers instead
of using an external API. In addition, McMaster's course outline policy and CEAB
requirements are written for people to interpret, so the team will need to
convert them into clear rules that the system can check automatically.

To test whether these risks are manageable, the proof of concept will use real
course outlines from the 2025-2026 academic year. The team will focus on
courses taken by one cohort, such as second-year Software Engineering students,
so that realistic assessment conflicts can be identified. The system will
extract assessment names, dates, weights, and learning outcomes from the
outlines and store them in a database. Any missing or unclear information will
be flagged instead of being ignored. The extracted results will be compared with
a manually prepared answer key to measure accuracy. If fully automated
extraction is not accurate enough, the team will use a semi-automated approach
where the extracted information is pre-filled and then confirmed or corrected by
a user.

The extracted assessment data will then be shown in a simple calendar that can
be filtered by course. The system will identify at least one week where students
in the selected cohort have multiple assessments due close together. For one of
these assessments, the solver will suggest alternative dates that reduce the
workload while still following important constraints, such as avoiding the exam
period, or changing lab due dates. If creating a complete constraint model
becomes too complex for the proof of concept, the team will use a simpler
scoring method that ranks possible dates based on student workload. This would
still show that the system can provide useful scheduling suggestions.

Each suggested date will also include a short explanation generated by an LLM.
For the proof of concept, the team plans to use a hosted LLM API. The
explanation will only use information produced by the scheduling system, such as
comparing how many assessments are scheduled in the original week versus the
suggested week. This makes the explanation easier to check against the actual
data. Only publicly available course outline information will be sent to the
API. The LLM component will also be designed so that it can later be replaced by
a model hosted on CAS servers without requiring major changes to the rest of the
system.

The proof of concept will also include a basic compliance checker. The sample
course outlines will be checked against a small set of rules from McMaster's
course outline policy, such as whether required sections are included and
whether assessment weights add up to 100\%. Any missing or incorrect information
will be listed for the user.

The user interface will be kept simple for the proof of concept. The goal at
this stage is not to build the final product, but to show that the data
pipeline, the optimization, and the explanation features work together. If the
team can successfully extract course information, identify workload conflicts,
suggest better dates, check basic policy requirements, and explain the
suggestions, it will show that the main technical risks can be handled before
moving on to the full system.

\section{Coding Standard}

The project will follow the following established coding standards to maintain consistency, readability, and maintainability across the codebase:

\begin{itemize}
\item \textbf{Frontend:} TypeScript and React code will follow ESLint and Prettier formatting rules.\texttt{camelCase} will be used for variables and functions, while \texttt{PascalCase} will be used for React components and types.

\item \textbf{Backend:} Python code will follow PEP 8. \texttt{snake\_case} will be used for variables and functions, and \texttt{PascalCase} will be used for classes.

\item \textbf{Database:} MongoDB documents will use consistent field naming and structure. Indexes will be used for frequently queried fields, and database operations will be separated from application logic.

\item \textbf{General:} Code will use descriptive names and consistent formatting. Comments will be used where necessary to explain non-obvious logic. Unused code and debugging statements will be removed before merging.

\item \textbf{Testing:} Backend code will be tested using Pytest and frontend code using Vitest or Jest testing library. Core functionality, API endpoints, and important application components will have corresponding tests where appropriate.


\end{itemize}

\subsection*{Why is it important to create a development plan prior to starting the project?}

Our system has several components that depend on each other, including data
extraction, the database, conflict detection, scheduling suggestions, and
compliance checking. Creating a development plan helps make sure everyone on the
team has the same understanding of how these components will work together and
what tools and formats will be used. It also helps us divide responsibilities
and agree on how we will use Git, track issues, and communicate throughout the
project. Having these decisions made early reduces confusion later and allows us
to focus the proof of concept on the areas that have the most technical risk.

\subsection*{In your opinion, what are the advantages and disadvantages of using CI/CD?}

One of the main advantages of CI/CD is that it can catch problems early by
automatically running tests whenever changes are made. This is useful for our
project because many parts of the system are connected. For example, a change to
the format of the extracted course data could affect the calendar, conflict
detection, or scheduling solver. CI/CD can help identify these issues before
they are merged into the main branch. It can also help keep the main branch
stable and make it easier to maintain a working version of the system throughout
development.

The main disadvantage is the additional time required to set up and maintain the
CI/CD pipeline. It is also only as useful as the tests included in it. If the
test coverage is limited, some problems may still go unnoticed. Certain parts of
our project, such as evaluating the quality and accuracy of LLM-generated
explanations, may also require manual testing rather than relying only on
automated tests.

\subsection*{What disagreements did your group have in this deliverable, if any, and how did you resolve them?}

Our group did not have any major disagreements while completing this
deliverable. Most decisions were made through discussion and agreement between
the team members. One topic that required more discussion was how the LLM should
be used in the system. We considered using an external API, hosting an existing
model on CAS servers, or potentially using our own locally hosted solution.

Since we have not yet had an official meeting with our supervisors, we do not
currently know the exact privacy and hosting requirements for the project. For
now, we agreed to use a hosted API for the proof of concept and only send
publicly available course outline information to it. We will also design the LLM
component so that it can be replaced with a locally hosted model later if
required. We plan to discuss the final hosting approach with our supervisors
during our first project meeting.
